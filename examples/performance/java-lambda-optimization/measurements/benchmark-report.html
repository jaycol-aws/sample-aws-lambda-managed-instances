Key finding. Across 240,000 requests and 10 independent runs, LMI delivers the best p50, p99, and tail latency for every workload type. CPU-bound work sees the largest gain (40% p50, 29× tail) from JIT C2 optimization. Memory-intensive work shows the biggest p99 improvement (47%) from eliminating cold-start GC pressure. I/O-bound work benefits from persistent connection pools (16% p50, 21× tail). LMI is also the most consistent mode — σ(p50) of ±3–5ms for CPU and I/O workloads.
Configuration. Standard, SnapStart, and GraalVM Native run at 1024 MB (1 vCPU) — the typical Java Lambda configuration. LMI runs with ExecutionEnvironmentMemoryGiBPerVCpu: 2 (minimum) and explicit heap sizing (-Xms512m -Xmx1408m -XX:+UseG1GC). LMI concurrency is tuned per workload: 3 (CPU), 5 (memory), 10 (I/O). All modes tested identically via API Gateway with standardized traffic: 500 warmup discarded, 2,000 measurement at 15 concurrency and 30 qps, repeated 10 times.

JIT warmup — the LMI differentiator

On LMI, the JVM’s C2 compiler profiles hot methods and optimizes them aggressively over hundreds of invocations. Measured with sequential invocations on a single LMI environment, the improvement is dramatic for CPU and I/O workloads.

Cold vs warm JIT p50
Use caseCold JIT p50Warm JIT p50Improvement
UC1 PDF (CPU-bound)482ms38ms12.7×
UC2 ETL (Memory)167ms162ms1.0×

CPU-bound and I/O-bound workloads see 12× improvement as JIT inlines methods, eliminates bounds checks, and optimizes hot loops. Memory-intensive work (UC2) shows minimal JIT gain because GC and allocation dominate — but LMI still wins on p99 through warm GC state.

GraalVM Native — error rates

An honest finding: GraalVM native image showed elevated error rates on complex workloads due to reflection and serialization edge cases in the DynamoDB Enhanced Client and Jackson under AOT compilation.

Recommendation. GraalVM native is excellent for simple, well-tested workloads with bursty traffic. For complex enterprise Java with heavy SDK usage, LMI or SnapStart are safer choices.

Methodology

ApplicationSpring Boot 3.4.3, Java 21 (Corretto), Spring Cloud Function, AWS SDK v2
Standard/SnapStart/Native1024 MB (1 vCPU) — typical Java Lambda configuration
LMI2 GiB/vCPU (minimum), -Xms512m -Xmx1408m -XX:+UseG1GC, concurrency 3/5/10 per UC
TrafficStandardized: 500 warmup (discarded) + 2,000 measurement @ 15 concurrency, 30 qps
Runs10 independent runs per mode per use case (240,000 total measurement requests)
PayloadsDeterministic (ACCT-1, DEVICE-1, CUST-1) for run-to-run consistency
LMI warmupFleet pre-warmed with 200 requests before benchmark for JIT C2 compilation
VPCLMI in VPC with DynamoDB + S3 Gateway Endpoints
Architecturex86_64 all modes. Production: consider arm64 (Graviton) for ~20% cost savings.
Memory note1024 MB Standard vs 2 GiB/vCPU LMI reflects the real-world choice, not an equal-resource comparison. At 2048 MB (2 vCPU), the p50 gap narrows significantly.
